# PCLR for LLaVA

This implementation provides PCLR for UCIT and MLLM-DCL. It is an independent implementation based on Meng et al., *PCLR: Progressively Compressed LoRA for Multimodal Continual Instruction Tuning*, ICLR 2026, [paper](https://proceedings.iclr.cc/paper_files/paper/2026/file/5a5acfd0876c940d81619c1dc60e7748-Paper-Conference.pdf). The local acquired paper has SHA-256 `fac4bede457c5b8ff73a6a3cf5ef738e9898297bcaa608aafa47a53f82fc0e53`. The official [repository](https://github.com/SII-HITclearlove777/PCLR), commit `d77497e2dc44a06709d8bf5c768d1ffbd7b8b721`, was audited. Its README states Apache-2.0 but the repository contains no `LICENSE` file at that commit. No source from that repository is included here. The PCLR evaluation and smoke runners adapt the existing Apache-2.0 MCITlib CoIN runners.

| Behavior | MCITlib implementation | Paper / release reference |
| --- | --- | --- |
| Per-layer rank pools and shared text/vision keys | `mcitlib/methods/_pclr/core.py`: `Keys`, `RankLinear`, `RankPool`; `llava.py`: `target_groups` and `queries` | §§4.1–4.2; `lrp/model/LrpModel.py`, `lrp/model/utils.py` |
| Input query, batch-aggregated top-k routing, train-key alignment | `llava.py`: `queries`, `RoutedLlava.forward`; `core.py`: `select`, `alignment_loss` | §4.2, Eq. 4; `lrp/model/LrpModel.py` `get_score`, `get_q_loss` |
| Merge new and old ranks, prune every 4th or 8th rank separately in old/new pools and realign retained keys with task prototypes | `RankPool.merge_new`, `RankPool.compress` | §§4.3–4.4 and appendix J; `lrp/model/LrpTSModel.py` `init_key_value`; released `*_2.sh` scripts |
| Shared rank consolidation and frozen teacher; task-prototype sampling weighted by recent distillation error; teacher top-100 temperature-2 KL | `RankPool.compress`, `RankLinear.forward`, `RoutedLlava.forward`, `distillation_loss` | §4.3, Eqs. 5–7; `lrp/model/LrpTSModel.py` and `lrp/train/LrpTS_trainer.py` |
| New ranks and keys, old/shared frozen; nearest-rank value initialization after the first consolidation | `RankPool.begin_task`, `init_new_keys` | §4.3; released `*_1.sh` scripts use `--init_value True` from task 5 |
| Boundary save/reload including rank values, keys, shared ranks, original projector and task-query history | `RankPool.save_boundary`, `load_boundary`; `llava.run`; `inference.py` | `lrp/train/train.py` boundary state and `lrp/model/LrpModel.py` generation |

Queries use the mean token embeddings of the first human instruction and the CLIP CLS feature, as in the released LLaVA path. The repository expects precomputed task key-initialization files that it does not provide. The implementation deterministically scans the complete current training dataset to compute the initial mean query; this extra full-data CLIP pass has a measurable cost and must not be silently removed. It is a concrete adaptation of the paper's subset-based initialization, and is not claimed to reproduce the unpublished precomputation exactly. One image per example is supported; doctor checks every query dataset and image, the prior task boundary/history and the required consolidation steps.

Training casts the base to the configured mixed precision and restores modules with `norm` in their names to FP32, matching the release. Query initialization, training, and generation use the base model's autocast dtype so that the CLIP tower can execute with FP32 norms. Inference restores FP32 norms after loading the base; the V4 LLaVA builder loads that base in FP16 by default, whereas the released training configuration uses BF16. It uses the V4 LLaVA data and tokenizer path; the released training script selects the slow tokenizer, whereas V4 normally selects the fast tokenizer.

The release scripts use 64 new ranks through task 6, then 32; top-64 rank routing, alpha 128, no dropout, and a 32-rank shared pool. Compression begins after task 4: retention is 75% (skip 4) after tasks 4 and 5 and 87.5% (skip 8) after tasks 6 and 7. The schedule is fixed to the released per-task scripts. Appendix J also describes using observed KL to decide when to change retention; this implementation does not implement that adaptive trigger. It consolidates after a benchmark's final task when the threshold is reached, following the paper's Algorithm 1; the released eight-task shell sequence omits consolidation after its last task. This distinction affects the final checkpoint and should be recorded when comparing results.

The main training stage uses the existing benchmark's full-data MCITlib budget: UCIT uses one epoch and nominal global batch 64 on two GPUs; DCL uses epochs `1,3,1,2,1` and nominal global batch 16. Main LR is `2e-4`. These DCL full-data epochs are MCITlib's dataset-size adaptation, not the paper's all-one-epoch CoIN setting. Under `llava_sample_unified`, main training uses 3,000 examples, one epoch, LR `2e-4` and global batch 64; the profile leaves the separate integration command intact. Each consolidation trains on the **current task's data** for one epoch at `5e-5`, with the command's recorded microbatch/accumulation and projector LR `2e-5`. Compression is performed at the start of this stage, before teacher–student integration. The single-process full-data query pass, integration epoch, and checkpoint writes add time beyond primary learning.

`pclr.pt` stores adapter state, task history, configuration and target paths. A later task must load the preceding boundary. A learned boundary contains the current task's new ranks; an integrated boundary contains the compressed ranks and shared ranks. Inference reloads the real base and checkpoint and invokes LLaVA generation with task-aware rank routing. Train and inference commands are assembled by the usual V4 registry/runner; `mcitlib doctor` checks dataset and stage dependencies. Resume markers are per command; a failed or interrupted training stage is restarted, not resumed from an optimizer state.

The original paper reports 4 × 80 GiB GPUs. This two-GPU implementation uses ZeRO-2 and BF16. As an order-of-magnitude estimate for 7B, the frozen base is about 14 GiB plus vision and activations; roughly 256 pooled ranks across LLaMA-7B projection layers are about 1.2–1.5 GiB in BF16, with teacher and student copies and optimizer state adding several GiB during integration. Budget at least 30–60 GiB per GPU for small microbatches; full 2,048-token training and larger batches may exceed this or 80 GiB. This is not a measured peak. Reserve at least 30 GiB free for checkpoints and temporary training files, in addition to already-installed base model, vision tower, and data. The bounded two-task validation run should use a new isolated directory and can require several GiB; outputs are not scientific results.

For a configured environment, inspect the planned stages and prerequisites before training:

```bash
mcitlib config validate
mcitlib doctor --method pclr --benchmark ucit
mcitlib train --method pclr --benchmark ucit --dry-run
mcitlib eval --method pclr --benchmark ucit --after-task 4 --dry-run
python -m tools.pclr_smoke --help
python -m tools.pclr_precision_probe --device cpu
```

The bounded smoke helper supports both benchmarks and performs two learning stages, a validation-only early consolidation, and real generation after reloading the integrated checkpoint. It runs at least two optimizer steps per stage with zero warmup for this diagnostic alone. It records per-stage evidence that the new B ranks changed and that consolidation changed the retained or shared B ranks; an absent update fails the smoke before generation. Its early consolidation and reduced step count are intended only to validate execution, not to report benchmark quality.
